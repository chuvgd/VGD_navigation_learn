# RoboMaster_Sentry算法技术报告

## 一.背景

本赛季哨兵算法的设计中，在参考与对比了23赛季华南农业大学开源的哨兵算法技术报告，23年哈尔滨工业大学开源的哨兵算法开源报告，24年中南大学哨兵算法开源代码框架，24年及25年深圳北理莫斯科大学哨兵仿真以及代码框架等论坛优秀开源文档下，选择了以**Point_Lio**为前端定位算法，**GICP**作为后段全局定位的修正，CMU的**terrainanalysis‌**地形高程分析作为感知，同时沿用**RM**赛场上大部分队伍一样使用的**ROS2 NAV2**作为整体导航框架，在哨兵决策方面，前期使用**状态机**进行维护，后期转向**行为树**进行设计。



## 二.目标

本赛季，我们希望哨兵能够做到稳定去击打前哨，并在击打完前哨后对后方基地进行守护和阻击从中央高地进行进攻的敌人，算法设计上围绕这个目标进行设计导航和决策模块，同时希望这套框架可以做到完全解耦以便于进行维护。



## 三.行动

整体的算法设计分为三大模块进行设计：1.定位与感知；2.导航的路径规划和运动控制；3.决策战术的设计

### 1.定位与感知

在前端定位与建图方面：对比github上主流开源的**FAST_LIO，FAST_LIO2，FASTER_LIO，POINT_LIO，LIO_SAM**等SLAM算法之后，我们选择了具有高鲁棒性和高频里程计输出的**POINT_LIO**算法，对于**POINT_LIO**这种激光雷达**IMU**紧耦合里程计算法，它不同于传统的**LIO**算法：

```
(1)提出了一种逐点 (point-wise) LIO 框架，该框架在实际采样时间融合激光雷达点，而不会累积到帧中。去除点累积消除了帧内运动失真，并允许以接近点采样率的高里程计输出和建图更新，这进一步使系统能够跟踪非常快的运动
(2)为了进一步提高系统带宽到超出IMU测量范围，用随机过程模型对IMU测量进行建模。将该模型扩展到系统运动学中，并将IMU测量值视为系统输出。即使IMU饱和，随机过程增强的运动学模型也可以平滑估计系统状态，包括角速度和线加速度
```

![POINT_LIO流程图](/home/ubuntu/ROBOMASTER报告/6ac1bfd8d3c5659cb955478f8cfd3a19.png)

**POINT_LIO**输出的里程计即位置姿态的信息极限情况下可以达到 ‌**4–8 kHz**频率更新，同时系统带宽 ‌**>150 Hz**‌，在极端激进运动下具有较高鲁棒性，不会出现整个观测系统的发散导致位置姿态估计出现较大错误——防止运动畸变，为后续哨兵的导航和决策提供极稳定的前提优势。



在全局定位的修正上：即对接后面的**NAV2**导航框架中的**map to odom**这个坐标转换上，我们采用**CICP**这种**SCAN TO MAP**大众化的点云配准思路，并在此基础上进行了一些优化，对于**GICP**这种点云配准思路上有优势和缺陷——但是对比下来，我们认为在**RM**这个赛场上，它的优势更加突出，而缺陷基本可以忽略。

```
(1)优势：在有一个先验PCD的情况下，给定一个良好的初始位置姿态估计即可很快维持一次初始重新定位，在后续比赛中也利用同样的道理，把LIO scan出去畸变pointcloud进行坐标转换后和先验点云进行配准以修正里程计的误差，且全局定位修正的结果实际测试下来十分准确
(2)缺陷：即如果初始位置姿态估计有较大偏差的情况下，极容易导致出现初始位置姿态配准的发散，即第一次初始重定位直接出现发散，配准失败之后直接导致后续的定位系统发散，但是由于比赛赛场启动位置比较固定，所以测试下来基本不会出现定位发散
```

而在算法设计上，GICP比起其他ICP，NDT点云配准上：

```
(1)将点云建模为概率分布，利用局部几何协方差与马氏距离替代传统欧氏距离，显著提升复杂场景下的精度、鲁棒性与收敛效率
(2)在平面丰富场景（如建筑、道路）中，比点 - 点 ICP 更敏感于法向对齐，误差更小，实际测试下，将雷达侧放置能同时扫到天花板和地面的情况下，由于天花板的特征点分布比较均匀和突出，地面提供法线配准的方向，每次收敛速率和配准精度比较高，极少数出现初始配准即发散的情况
```

我们在和其他队伍交流下，对于GICP的配准频率有几种选择——(1)第一次初始重定位修正**map to odom**，后续关闭GICP配准以降低占用率和提升计算机性能，同时后续的定位只依靠前端里程计，这样的设计在我们后续测试下来，发现容易在回到补给区进行补给时出现0.5m到1m的定位误差，容易出现再次出补给区进行任务无法精准到点或者无法完全回到补给区进行补给，故放弃了这种思路；(2)在每次到固定的点进行一次GICP配准，同样也会出现(1)中一样的情况；(3)最后，我们决定以**5hz**的频率去进行GICP配准，在多次循环测试过程中，在自瞄和导航相关代码全部运行的情况下也不会出现特别高的占用率和计算机性能下降(大概55的占用率)


感知方向：环境感知指的是机器人对于周围障碍物、地形的辨识能力。简单的解决方法如 **Nav2** 中**costmap**的**obstacle_layer**，将输入点云中高于一定高度阈值的点分类为障碍物

对于感知方向，我们直接采用了深圳北理莫斯科大学的思路，只对实际上车后进行了参数修正，以下来自他们的报告思路：

```
1.坡面识别
使用 CMU 开源的 terrain_analysis。 大致流程： 点云预处理。裁剪仅保留车体周围一定范围的区域，通过下采样降低数据密度，并将点云按体素网格结构存储，以提高处理效率。 动态体素滚动更新。根据车辆实时位置动态调整体素网格布局：当车辆移动超出当前网格中心范围时，循环平移体素阵列，确保处理区域始终围绕车体，同时清理边缘旧数据。 地面基准高度计算。对每个体素内的点按高度排序，选取分位数高度作为地形基准。若存在地面抬升限制，则对基准高度进行约束，避免过度抬升。 高程差与障碍物标记。计算每个点相对于所在体素基准的高度差，点的高程信息被存储在点云消息的 intensity 域，通过将 intensity 高于一定 阈值的点辨识为障碍物即可实现障碍物和的辨识
1.原生对接 NAV2 框架
参考 nonpersistent_voxel_layer 创建了 intensity_voxel_layer，由于 terrain_analysis 已经将地形结果保存在点云的 intensity field 中，因此可以直接通过 intensity 值判断是否为障碍物，并将 3D 障碍物点云拍平到 2D 栅格表示。
```

### 2.路径规划和运动控制

路径规划方面：我们尝试了很多**nav2**原生的路径规划器，但是都发现了其由于栅格二值地图出现的路径规划下贴着高代价栅格走和路径不够平滑的问题，为了解决上述问题，我们从两个方面入手——1.对接**nav2**原生的路径规划优化器**savitzky_golay_smoother**，直接对生成的路径进行几何学优化，使其更平滑，但是还是不能够解决对路径规划下贴着高代价栅格走的问题，于是我们转而研究——**安全走廊**和**B样条**有关的优化；2.即安全走廊的引入和B样条的优化，对先前的采样路径作为原始输入，然后加以对路径过程出现的障碍物栅格进行膨胀生成一个个**凸边型走廊**，让机器人规划路径避开相关障碍物栅格，最后对原始输入的路径进行**B样条**的相关二次规划

![](/home/ubuntu/ROBOMASTER报告/2026-08-25_14-18.png)

```
(1)为了得到比较稀疏的运动走廊，膨胀分为两步。第一是基于前端得到的path节点进行膨胀，但是加了一个限制条件，即已经被bounding box覆盖的节点不予膨胀，这样的好处是不用再扩展冗余的box以及为了下一步的简化减少了很大的计算量。第二是对得到的bounding box进一步简化，因为前一步得到的bounding box仍然存在大量重叠的情况，对接下来的轨迹优化来说无疑是无用且消耗计算的，这里简化的核心思想是从当前boxNow开始按照顺序找到其不相交的boxA，并将该boxA的前一个boxB保留下来，并删除从boxNow到boxB之间的所有box,然后boxA作为新的boxNow继续删减
(2)B样条优化主要参考资料为《Online Safe Trajectory Generation For Quadrotors Using Fast Marching Method and Bernstein Basis Polynomial》、《Minimum snap trajectory generation and control for quadrotors》、https://www.bilibili.com/video/BV1hs4115713
```

![](/home/ubuntu/--original--Trajectory-optimization-based-on-Bezier-polynomial-motion-planning-/result.png)

运动控制上：我们直接采用了**nav2**的**纯追踪算法**输出**cmd_vel**和**下位机PID控制**，没有过多对算法上的优化，只进行了实车参数调整，基本实现速度的平滑输出，下赛季可以尝试其他控制算法对速度输出进一步优化和改进。
